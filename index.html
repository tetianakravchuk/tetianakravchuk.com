AI systems quality engineering

How I evaluate whether an AI system is ready to release

I separate source evidence, deterministic safety, human approval, recovery behavior, and release evidence. These examples show the checks I use to investigate failures and preserve uncertainty.

Recover from source failures safely

Five Sweden discovery runs initially reached a dead-letter state after remote connections closed. After a targeted network-error fix, five sequential runs reached human review with 22 verified and three pending sources per run. Timed-out sources stayed pending after retry exhaustion; run-specific golden-set evidence was still outstanding at that milestone.

Test the evidence behind a decision

I reproduced a defect where changing a claim’s expected value changed its proposed verdict but left the evidence receipt hash unchanged. A regression test exposed the gap; the fix bound the expected value into the receipt. The focused suite moved from nine to ten passing tests.

Keep safety and human approval explicit

WPH uses verified, rejected, and verification-pending outcomes. Agent proposals require human review; automatic promotion and trusted-path access remain disabled. Rights safety is a hard gate and cannot be averaged away.

Make release confidence auditable

I report code tests, isolated PostgreSQL checks, deployment identity, and persisted production evidence separately as PASS, FAIL, BLOCKED, or NOT RUN, with supporting run and receipt references.
